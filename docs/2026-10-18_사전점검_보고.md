## 3. 사고: 부하테스트 알림톡 오발송 208건

- **경위**: 15:26 k6 부하테스트를 시작하면서 알림 템플릿을 끄려던 SQL이 권한 분류기에 막혔는데 k6는 이미 시작됨 → 임의 번호(010-5xxx)로 접수된 53건에 알림톡 실발송. 즉시 중단·행사 closed 처리. 15:30 k6 번호를 테스트 번호대로 바꿔 재실행했으나 **현장대기 시나리오 하나('0106' 대역)를 놓쳐** 155건 추가 발송.
- **피해**: 모르는 번호 208명에게 "[플릿 테스트 행사] 대기 접수 완료" 알림톡(카카오 미가입 번호는 SMS 대체). 비용 약 2천 원. 수신자 민원 가능성 있음 — 문의 오면 "시스템 테스트 중 오발송, 개인정보 수집 없음(번호는 즉시 삭제)" 로 안내. 해당 티켓 전화번호는 전부 NULL 처리 완료.
- **재발 방지 (적용 완료)**
  1. notify 함수 v8: `010-00xx-xxxx` 번호대는 어떤 경우에도 실발송하지 않고 `skipped(TEST_NUMBER)`.
  2. DB 트리거: 이름이 `k6*` 인 티켓은 그 번호대가 아니면 insert 자체 거부 (0024).
  3. k6 스크립트: 번호 생성기를 `testPhone()` 하나로 통일. `loadtest/trigger` 에 경고 주석.
  4. 교훈: **실발송 가능한 환경에서 대량 생성 테스트를 돌리기 전에 차단 장치가 "실제로 적용됐는지" 먼저 1건으로 확인**한다. 오늘은 순서가 거꾸로였다.

## 5. 개선점 (우선순위순 · 행사 후 처리)

### 운영·UX
1. **알림 테스트 모드 스위치**: 행사(또는 전체) 단위 `notify_mode: live|dry|test_numbers_only` 를 관리자 화면 토글로. 오늘처럼 SQL 로 끄려다 막히는 일 방지.
2. **스태프 "대기로 복구" 확인창**: 브라우저 `confirm()` 대신 인앱 모달. iOS 홈화면 앱(PWA)에서 confirm 이 어색하고 자동화도 안 됨.
3. **예약 화면 날짜 탭**: 4개 이상이면 두 줄로 접힘 → 가로 스크롤 칩으로.
4. **당일 예약 리마인드**: 매일 12:00 오픈 구조에서는 "전날 19:00" 리마인드가 의미 없음. 설정 기본값을 "시작 30분 전" 하나로.
5. **스태프 PIN 분실 대응**: 관리자 화면에서 PIN 을 다시 보여줄 수 없음(해시). 재설정만 가능 → 매뉴얼에 명시 (반영함).
6. **관리자 화면 자동 점검**: 접속 코드 로그인 때문에 자동화 못 함. 테스트 전용 코드 + 테스트 행사로 E2E 스크립트화.
7. **부하테스트 중복 번호**: `testPhone()` 랜덤 6자리라 600건 중 1건 충돌. 시퀀스 기반으로.
